# Contributing Guide

Thank you for contributing to this repository.

This project is part of the proyectos_sena ecosystem and aims to provide a professional, educational, and reusable backend API template.

---

# Purpose

The objective of this repository is to provide:

* Backend architecture guidance
* Documentation standards
* Educational examples
* Professional project organization

Contributions should support these goals.

---

# Contribution Principles

Every contribution should improve at least one of the following:

* Architecture
* Documentation
* Examples
* Learning experience
* Repository organization
* Development workflows

---

# Before Contributing

Please review:

* README.md
* docs/architecture.md
* docs/api-reference.md
* docs/database-schema.md
* docs/deployment.md

Understanding the repository structure helps maintain consistency.

---

# Repository Philosophy

This repository is:

```text
Architecture First
Documentation First
Technology Agnostic
Educational Oriented
```

This repository is NOT:

```text
A production application
A specific framework implementation
A code-only repository
```

---

# Branch Strategy

Use the following branch naming convention:

```text
feature/*
fix/*
docs/*
refactor/*
chore/*
```

Examples:

```text
feature/docker-support
feature/postgresql-example

docs/update-deployment-guide
docs/improve-readme

fix/example-structure

chore/update-github-workflows
```

---

# Commit Convention

Follow Conventional Commits.

## Feature

```text
feat: add docker deployment example
```

## Fix

```text
fix: correct architecture diagram
```

## Documentation

```text
docs: improve fastapi guide
```

## Refactor

```text
refactor: reorganize examples structure
```

## Chore

```text
chore: update repository metadata
```

---

# Pull Request Guidelines

A pull request should:

* Have a clear objective
* Be focused on a single topic
* Include updated documentation when necessary

Avoid:

* Unrelated changes
* Large mixed-purpose pull requests
* Breaking repository organization

---

# Documentation Standards

Documentation should be:

* Clear
* Concise
* Educational
* Technology-agnostic when possible

Prefer:

```text
Explain why
Explain when
Explain how
```

Not simply:

```text
Explain what
```

---

# Architecture Contributions

When proposing architectural changes:

Provide:

* Motivation
* Benefits
* Trade-offs
* Impact on existing structure

Questions to consider:

* Does this improve maintainability?
* Does this improve learning value?
* Does this remain language agnostic?
* Does this align with professional practices?

---

# Example Contributions

Examples should demonstrate:

* Real-world practices
* Clean architecture
* Separation of concerns
* Testing approaches

Examples should remain:

* Small
* Focused
* Educational

Avoid overly complex examples.

---

# Documentation Structure

New documentation should be placed in:

```text
docs/
```

Technology-specific documentation belongs in:

```text
docs/technologies/
```

Examples belong in:

```text
examples/
```

---

# Quality Checklist

Before submitting a contribution:

* [ ] Documentation reviewed
* [ ] Structure follows repository standards
* [ ] Naming conventions respected
* [ ] No unnecessary files included
* [ ] Examples remain educational
* [ ] README updated if needed

---

# Files That Should Not Be Committed

Do not commit:

```text
node_modules/
venv/
.venv/
.env
__pycache__/
dist/
build/
```

Use .gitignore appropriately.

---

# Review Criteria

Contributions are evaluated based on:

* Clarity
* Educational value
* Maintainability
* Consistency
* Alignment with repository goals

---

# Code of Conduct

Contributors should:

* Be respectful
* Be constructive
* Focus on learning
* Encourage collaboration

Professional communication is expected.
